# 项目实施守则

## 第一版原则：先完整可玩，保留正常兜底，不做过度预防

第一版的首要目标是尽快跑通完整游戏闭环：

```text
进入世界 → NPC 自主行动 → 邀请与聊天 → 玩家干预 → 状态沉淀 → Day7 结算
```

所有设计和代码遵守以下规则：

1. **可玩闭环优先**：先让主流程从开局运行到结局，再优化单点质量和工程完备度。
2. **常见故障正常兜底**：输入错误、配置缺失、资源不存在、核心状态冲突、网络超时、限流、模型格式错误、重复请求和写入中断等正常风险必须有明确处理。
3. **罕见风险不过度预防**：没有真实故障或测试证据时，不为千分之一量级的极端情况提前添加复杂重试、熔断、自动修复、多级缓存、多模型复核、分布式锁或兼容层。
4. **单一路径优先**：同一能力第一版只保留一个清晰实现；暂不同时维护多套数据库、模型协议、调度器或状态来源。
5. **兜底必须简单可靠**：常见瞬时故障可以超时、有限重试或安全回退；失败后仍需返回明确错误并保留可重试状态，不能猜测或伪造剧情结果。
6. **抽象必须服务当前需求**：只在已经出现第二个真实实现或能明显隔离领域边界时增加接口和抽象层。
7. **测试围绕核心体验**：优先测试世界时间、聊天约束、信息隔离、状态提交和结局判定；低风险边角情况延后。
8. **延后项明确记录**：当前不做的能力写入阶段文档，不能为了“以后可能需要”提前实现。
9. **前端前先验证智能体玩法**：开发正式前端前，依次完成真实 Embedding、25 条关系 Memory、三条真实七日模拟路线，以及基于模拟证据的 Prompt/玩法调参。不能用 Fake 模型测试代替真实玩法验收。

发生取舍时，先判断风险是否常见、后果是否严重。常见或会破坏数据/泄露信息的问题必须处理；仅理论上可能且成本很高的极端问题延后。随后优先选择代码更少、状态来源更少、调用链更短，并且能够支撑完整玩法验证的方案。
